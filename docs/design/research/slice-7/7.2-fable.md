# 7.2 review: the node's anchoring simplified (pin D′, C2/C3/C5)

Branch `s7/7.2`, `62981f95..baca1272` (five commits). Read-only review
against pin D′, `simplify.md` C2/C3/C5, `plan3-fable.md` M1/M2 and
`7.1-fable.md` L4. `cargo test -p vos-venue --features
model,kreivo,kreivo-mock`: 39 passed (every venue code through each
table, the conformance vectors, the queue).

**Verdict: fix-then-merge.** The safety core holds: an honest cluster
cannot sign two roots for one window, the leader signs only a replicated
row, and no client sends over another root unless the leader offered it
after reading that root. Two Medium findings (one a regression the
removed `key_refused` memo used to prevent, one a consequence of the
guard's veto) and a handful of small ones.

## What holds (the safety matrix asked for)

- **Two roots for one window from an honest cluster: no.** The row is
  `space_root(space, w, cut_root)` written by `Finish::write`
  (`node/host/src/roots/cuts.rs:357-361`) from the cut root alone; the cut
  root is fixed by the committed log (slice 6's checker invariant, now
  extended to anchor rows). The leader signs only `roots::anchors` rows
  (`leader/anchor.rs:158`), never a batch under proposal (`leader/mod.rs:203-205`
  runs `anchor()` before `run()`). A deposed leader and its successor hold
  the same row; the venue answers `Again`/`AlreadyAnchored` → `Taken`. A
  lagging replica has no row yet → `anchor_wait` is `None`, nothing is
  offered. A replica that installs a snapshot receives the exporter's rows
  (`store/read.rs:30-78` exports the whole agent partition; the cuts suite's
  `by_snapshot` case asserts the cut root arrives) so it holds the same
  bytes. Clock skew: `aged` is judged by the venue's time when read; the
  node clock only drives the handoff damper.
- **Writing the row at the cut-build commit, not at `Input::Close`'s
  apply:** sound. `closing()`'s *paths* depend on the asks table as read
  at build time, but the anchor row depends only on the cut root, so a
  replica that builds late still writes the same 32 bytes. The departure
  is well argued (no agent-image change); but pin D′'s text in
  `slice-7-mobile.md:171-183` still says "by apply" and "if any differs"
  — see L7.
- **No client sends over another root without the leader's say:** Kreivo
  (`venue/src/kreivo/venue.rs:521-525`, `send.rs:99-102`) and JAM
  (`tools/jam-dev/src/venue.rs:559-568`, `:314-319`) both mark `evidence`
  only inside `anchor()` when the cache already holds another root, which
  the leader reaches only via `Held::Root(_)` → `guard()` → `offer()`
  (`anchor.rs:180-184`). A stale `last` cannot leak evidence: the
  pre-send read `held_before` sees the other root, caches it and drops
  (`send.rs:99-101`), and the next pass goes through the guard.
- **Aged windows settle unsent** (`anchor.rs:169-171`), in order; the
  rows are pruned at `MaxRootAge` (`cuts.rs:362-370`).
- **C5 tables:** model (`model.rs:357-369`), Kreivo (`send.rs:366-381`,
  `every_error_and_refusal_is_mapped`) and JAM (`venue.rs:410-419`,
  `each_anchor_code_has_its_outcome`) match `spaces-pallet.md` §6.1/§9.
  `SubmitOutcome::judged` is right: `Repeated` is `Seen[id]` and the id
  covers program, space and io-hash (`pvm/proof/statement/src/lib.rs:231-240`),
  so a repeat is the same statement (format excluded by design).
- **Prover worker:** `Retry(code)` counts toward `MAX_RESUBMITS` only in
  `[UNJUDGED_FROM, UNJUDGED)` (`node/prover/src/worker.rs:656-665`); the
  rest retry with doubling waits until `dead`. 4 resubmits then
  `Refused(code)`, as the doc says.
- **Removed code:** rotation and the hand-back dropped nothing that still
  matters under C2/C3 (the "foreign anchor" check was a hand-back check;
  the structural replacement is stronger). The `key_refused` memo is the
  exception: M2 below.

## Medium

### M1. A single dissenting replica settles the window for the leadership: evidence suppressed, the forged root stands

- **Where:** `node/host/src/leader/anchor.rs:185-188` (`Guard::Differs` →
  alert, `true` → `settled` advances past `w`), `:306-308`.
- **Scenario:** a compromised replica (its node key *is* a listed key)
  anchors a forged `R'` at `w` first. The honest leader sees
  `Held::Root(R')`, asks the replicas; the compromised one answers any row
  ≠ `R`. The leader alerts "divergent replicas" and settles `w`: no
  evidence this leadership, ever, even after the operator replaces that
  replica (replacement does not change the leader, and `settled` never
  goes back). `R'` stands at the venue for up to `MaxRootAge` (24 h):
  statements over the attacker's root are accepted, the honest root's
  refused `Unanchored`, and the alert points the operator at "an apply
  bug or a clone". Before the guard (7.1) the honest evidence ended the
  space, which gave the attacker nothing. The pin asked for "if any
  differs it sends nothing", so the veto is per spec; the *permanent
  settle* is not, and it is what turns a 2 s delay into a 24 h window.
- **Fix (keeps the pin's rule):** on `Differs`, do not settle: `return`
  as `Unsure` does (the recheck re-asks every 2 s, the alert is deduped),
  so the evidence goes once the dissenter is replaced or heals. Carry the
  dissenting root in `AnchorAlert::Divergent` and say in
  `docs/operations.md` what it means: a row equal to the venue's held
  root names the equivocator (a fork of this representative); one equal
  to neither is a bug or a compromise. Whether a quorum should override a
  dissenting minority is the owner's call (`plan3-fable.md` M1 chose the
  veto); record it either way.

### M2. Removing `key_refused` reopens a fee-per-block churn on Kreivo's `NotAuthority`

- **Where:** `node/venue/src/kreivo/send.rs:188-196` (on `Unlisted` the
  client drops the signer from `known.keys` and asks for a refresh);
  `venue.rs:836` (`refresh` overwrites `known.keys` from `AnchorKeys`);
  `venue.rs:514-533` (`anchor()` answers `Taken` and queues whenever the
  cache lists the key).
- **Scenario:** `operations.md` step 4 says "remove the old node's key
  (and, on Kreivo, its authority)". Kreivo refuses `remove_anchor_key` of
  a paired key (`AnchorKeyInUse`, G14), so the operator removes the
  authority first. Between the two steps `AnchorKeys` still lists the key
  while the account is no authority: the pallet answers 7
  `NotAuthority`; the client drops the key; the next refresh (2 s)
  re-adds it; the leader's recheck offers again; `ready` passes; the call
  goes; refused; a fee charged on the node's own account (a non-authority
  pays its own fee), once a block, until the key is removed or the
  account empties (`Payment`). Pre-7.2 the leader's `key_refused`
  memo held `(listing, now)` and stopped re-signing until the listing
  changed, exactly this case. JAM is unaffected (`Key` and the record
  agree).
- **Fix:** keep a per-`(space, signer)` "refused under this listing"
  memo in the Kreivo client, set on 7/11 with the `keys` vector read, and
  cleared only when a refresh reads a different `AnchorKeys` (the old
  memo's rule, moved to the client where the cache is). Or map 7 to
  `NotYet` with `Fate::Again(length_ms)` and an alert. Add a unit test: 7
  refused, refresh re-reads the same listing, no second call. And reorder
  `operations.md`'s step 4: authority, then key, in one sitting.

## Low

### L1. The guard waits for *every* replica, on the batch thread, before each batch

- **Where:** `anchor.rs:297` (`while agreed < group`), `leader/mod.rs:205`
  (`anchor()` before every batch), `GUARD_WAIT` 2 s.
- **Scenario:** the venue holds another root at `w` and one replica is
  down: every pass waits the full 2 s (quorum alone does not end the loop,
  since dissent must be ruled out), and a pass runs before every batch,
  so the representative's batches are 2 s apart until the client reads
  the space ended. With `Unsure` (no quorum) this repeats indefinitely,
  though Raft commits nothing then either.
- **Fix:** run `anchor()` only when `anchor_wait()` is due (the 2 s
  recheck or `Woke::Built`), not before every batch; the module doc's
  "before each batch" then changes to "after each cut built, and every
  2 s while a row waits".

### L2. After offering the evidence the loop goes on offering later windows

- **Where:** `anchor.rs:181-184, 191-194, 197-200`: `Offered::Taken` for
  the evidence window leaves `settling = false` but does not `return`;
  the later rows are `Held::Nothing` → offered → queued.
- **Scenario:** Kreivo's `ready` reads the cached status (`Active` until
  the next refresh), so one or two later anchors are sent and refused
  `SpaceNotActive`, a fee each, plus a `Stopped` alert per window.
- **Fix:** `return` after an offer made over `Held::Root(_)`.

### L3. The operator surface has no "this node sent the evidence" event

- **Where:** `anchor.rs:54-74` (`AnchorAlert` has `Stopped`, no
  `Evidence`), `:176-179` and `:236-239` raise two different `Stopped`
  alerts (`code: 0` from the status, then the venue's code) for one
  event; the model's `Stopped(8)` is the only hint.
- **Fix:** `AnchorAlert::Evidence { window }` raised in `anchor()` when
  the guard agreed and the offer was made; `operations.md`'s "stopped"
  bullet then splits "blocked" from "ended, this node's anchor the
  evidence". The Kreivo client's `Alert::Equivocation` exists but is not
  in `Node::anchor_alerts`.

### L4. `aged` falls back to the node clock before the venue's time is read

- **Where:** `anchor.rs:166` (`venue.time().unwrap_or_else(node clock)`),
  judged at `:169` *before* `held()`'s `Unread` early return.
- **Scenario:** a node whose clock runs a day ahead, started while the
  venue is unreachable, settles every waiting row `Never { code: None }`
  for this leadership without sending; a later leadership would retry,
  but on a single-node representative there is none.
- **Fix:** with `venue.time()` unread, `return` (as `Held::Unread` does);
  the venue's clock alone judges age, as the pin says.

### L5. The handoff damper is per leadership, not per node

- **Where:** `anchor.rs:89-100` (`Anchoring` is rebuilt by
  `Leader::open`), `:247-251`.
- **Scenario (M2(b) in plan3):** A and B both delisted, each client's
  listing one refresh stale: A hands to B, B's own cache says B unlisted
  and still lists A, B hands back; each hop is a new leadership with
  `handed = None`, so the pair ping-pongs until the caches refresh (one
  refresh, a few elections). Also `open.is_none()` (node clock before the
  space's origin) disables the damper entirely (`:250`).
- **Fix:** keep `handed` on `Inner` keyed by agent, or refuse a handoff
  within one client refresh of a leadership's start; treat
  `open == None` as "handed this window".

### L6. The `CannotRun`/`Unconfirmed` race the e2e hit exists in production too

- **Where:** `node/host/src/node/mod.rs:207-222` (`may_represent` reads
  the venue client's cache), `admin.rs:62-67` (`create_representative`),
  `directory.rs:475` (`could_run_here` refuses the representative's
  record while the cache is empty).
- **Scenario:** an operator creates the representative, or restarts a
  node, within a refresh of the venue client connecting: `CannotRun` with
  no hint why; the record is recovered later only when Raft traffic
  prompts `should_ask`. Pre-existing (6.14b had the same dependency), but
  the record names the symptom and `operations.md` does not.
- **Fix:** answer a distinct `Unplaced::VenueUnread` (or wait for the
  first read, bounded) and say so in `operations.md`.

### L7. Pin D′ and `operations.md` lag the code

- **Where:** `docs/design/slice-7-mobile.md:171-183` (pin D′: "writes
  `anchor(w)` by apply"; "if any differs it sends nothing"), amended
  nowhere in this diff; `docs/operations.md:49-51` ("tries to hand off
  again once a window": with none listed it checks every 2 s and hands
  off as soon as one is listed; the damper applies after a handoff),
  `:58-62` ("stop the replica that differs": the alert cannot say which
  side is right, see M1), `:29-30` (Kreivo's order: authority before key,
  see M2), `:26-28` (the verb is `vos agent replace`; flags are right).
- **Fix:** amend pin D′'s two sentences (cut-build commit; a quorum
  holding the root and none differing) with a pointer to the record; fix
  the three runbook bullets.

## Info

- `send.rs:162-165`: 14 `AlreadyAnchored` as an error (a race between
  `held_before`'s read and the send) returns `Fate::Done` without
  `state.held(anchor)`, so the leader re-offers once before the cache
  catches up; harmless, `state.held(anchor)` there is right.
- `store/read.rs` exports the whole agent partition, so a
  snapshot-installed replica's anchor rows are the exporter's bytes, not
  an independent build: its guard vote echoes the leader's. Worth one
  sentence in `anchor.rs`'s module doc.
- `worker.rs:420-425`: the uncounted `Retry` wait doubles without bound
  (`Duration * 2` would overflow after ~58 doublings; in practice never,
  but a cap at a window's length reads better).
- The leader logs `Never { window: 0, code: 15 }` as an error for the
  window before registration, which the record calls routine for the
  Kreivo client; the leader's alert could skip `WindowNotAfterLast` for
  windows below the venue's `start_window` once `Status` carries it.

## Simplicity

The leader's anchoring is genuinely simpler to reason about: four fields,
one recheck, the signing input structural. The 229-line node shrink is
honest given C9–C11 are 7.3's; jam-dev's +283 is pin D′'s own ask (reads
off the batch thread) and mirrors Kreivo's reader. Comments are timeless
(the `0x0f` reservation note is the right kind). `AnchorAlert`'s dedup
"once until another" means two alternating alerts log every pass; a
per-variant dedup would be quieter.

## Verdict

**Fix-then-merge.** M1 (don't settle on `Differs`; name the root) and M2
(the client-side refused-under-this-listing memo, with its test and the
runbook's step order) before merge; L1–L4 are one-liners worth folding in
now; L5–L7 and the Info items may ride the 7.3 pass.
